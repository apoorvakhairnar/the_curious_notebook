# AGENTS.md — Dynamics That Compute

This file applies to everything inside the `dynamics_that_compute/` folder.

It adds local rules to the root `AGENTS.md`.

## Module purpose

`Dynamics That Compute` is a module inside `The Curious Notebook`.

The module explores physical systems, dynamics, and reservoir-computing ideas through simulations, explanations, and carefully framed experiments.

This folder may contain:

- module landing pages
- individual simulation pages
- supporting code
- generated figures
- notes about physical reservoir computing
- links to glossary terms
- lightweight demos or notebooks

The module should remain self-contained, but it should still feel like part of the larger website.

## Human role

The human author decides:

- what physical systems are worth simulating
- what equations are acceptable
- what assumptions are scientifically reasonable
- what input/output tasks make sense
- what counts as useful PRC evidence
- what figures are meaningful
- what results are ready to publish
- how strongly claims should be stated

Agents help build, organize, test, visualize, and document the work. Agents do not decide whether a result is scientifically meaningful.

## Simulation and PRC rules

When working on simulations, prefer outputs that expose:

- `t`: time vector
- `u`: input signal
- `X`: reservoir state matrix
- `y`: target signal, if applicable
- metadata/config with parameters, seed, solver settings, and task description

When evaluating PRC behavior, consider:

- state richness
- fading memory
- short-term memory capacity
- nonlinear memory capacity
- delayed input reconstruction
- NARMA-style tasks when appropriate
- train/test split correctness
- ridge or linear readout baselines
- direct-input baselines
- shuffled-state baselines
- robustness across seeds and parameter settings

Do not claim a system is a useful Physical Reservoir Computer from an attractive trajectory, animation, or single metric alone.

## Quarto rules inside this module

- Use `index.qmd` as the main page for each entry.
- Keep code in `code/`.
- Keep generated or hand-selected figures in `figures/`.
- Use relative links carefully.
- Link glossary terms when they help the reader.
- Use callouts for assumptions, limitations, and toy-model warnings.
- Avoid making ordinary `quarto render` rerun expensive simulations.
- If a figure is generated by code, document the generating script.
- Include alt text or an alt-text TODO for important images.

## Figure and animation rules

Figures and animations should support explanation, not replace evidence.

For generated visuals:

- label axes
- include units when known
- include captions
- avoid misleading scaling
- save outputs with descriptive filenames
- keep raw exploratory outputs separate from polished figures when possible
- avoid huge media files unless approved

## Content tone

The tone should be:

- curious
- careful
- explanatory
- honest about limitations
- readable by motivated non-specialists
- still useful for technical readers

Good phrasing:

- "This toy model lets us ask..."
- "The result suggests..."
- "This is not enough to prove..."
- "A stronger test would be..."
- "The reservoir-like behavior would need to survive..."

Avoid phrasing like:

- "This proves..."
- "Clearly this is a good PRC..."
- "The system computes because the plot looks complex..."

## Local quality checklist

Before treating a page or simulation as ready, check:

- the page renders
- local links work
- code paths are relative and reproducible
- generated figures are stored in `figures/`
- expensive code is not rerun unintentionally
- claims match the evidence shown
- train/test splits are described for PRC evaluations
- baselines are included or marked as TODO
- limitations are stated clearly
